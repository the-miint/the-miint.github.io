## ABSOLUTE HARD REQUIREMENTS
- NEVER use `rm` without permission. This includes `make clean` (`rm -rf site docs/duckdb-miint`).
  `make sync`/`serve`/`build` also wipe and regenerate `docs/duckdb-miint/` (via the sync script);
  that directory is a gitignored build artifact, so running them is fine.

## Project Overview

**the-miint.github.io** is the GitHub Pages site for the-miint organization, served at
https://the-miint.github.io/ and built with MkDocs + Material for MkDocs. We currently focus on
[duckdb-miint](https://github.com/the-miint/duckdb-miint) and [Qiita](https://github.com/the-miint/Qiita).
We provide a WASM "playground" which runs DuckDB and the MIINT extension entirely in the browser.

This repo is the **site shell**: landing page (`docs/index.md`), Qiita overview (`docs/qiita/`),
playground (`docs/playground.md`), theme and nav (`mkdocs.yml`), and brand
(`docs/stylesheets/brand.css`, `docs/assets/`). The duckdb-miint docs are **not** stored here (see below).

## Commands

Run inside the `miint-site` conda env (`conda activate miint-site`, or prefix with `conda run -n miint-site`).

```bash
make serve    # sync duckdb-miint docs + live-reload preview at http://127.0.0.1:8000
make build    # sync + `mkdocs build --strict` into ./site (what CI runs)
make sync     # only re-pull duckdb-miint docs into docs/duckdb-miint/
make test     # build + playground browser tests (see Verification)
```

- `MIINT_DOCS_SRC=../duckdb-miint/docs make serve`: sync from a local checkout instead of cloning
  (tutorials are read from its sibling `../onboarding-tutorials/`).
- `MIINT_DOCS_REF=<branch|tag|sha>`: pin the cloned ref (default: duckdb-miint's default branch).
- To verify without re-syncing or touching `./site`: `mkdocs build --strict -d <scratch dir>`.

## Architecture

### duckdb-miint docs are synced, never edited here
- `docs/duckdb-miint/` is generated by `scripts/sync-duckdb-miint-docs.sh` and gitignored. Never edit
  or commit it; the next sync deletes local edits. Content changes go to the-miint/duckdb-miint
  (its `docs/` and repo-root `onboarding-tutorials/`).
- The sync script applies build-time transforms to the copy: drops `UPDATING.md`, renames
  `table_of_contents.md` → `index.md`, points `../THIRD_PARTY_LICENSES.md` at GitHub, and rewrites
  the tutorials' `../docs/` links. A link that breaks only on this site usually needs a transform here.
- The duckdb-miint section of `nav` in `mkdocs.yml` hand-lists upstream filenames, and `validation:`
  in `mkdocs.yml` makes `--strict` fail when the two drift apart:
  - An upstream **rename or removal** fails with "A reference to ... is included in the 'nav'
    configuration, which is not found".
  - An upstream **addition** fails with "pages exist in the docs directory, but are not included in
    the 'nav' configuration". Add it where upstream's `table_of_contents.md` lists it.
- `--strict` also fails on broken links, including broken `#anchor` links. When the broken link is in
  upstream content, fix it in the-miint/duckdb-miint. Use a sync-script transform only for links that
  break solely on this site.
- So an upstream doc change can fail the nightly deploy; the live site stays on its last good build
  until the nav here (or the doc upstream) is fixed.
- Heading ids use GitHub-style slugs (`toc.slugify` in `mkdocs.yml`) because upstream docs are also
  read on GitHub and their `#anchor` links are written for it. Keep the two slug schemes aligned.

### Playground (`docs/playground.md`)
A self-contained page of raw HTML, CSS, and a `<script type="module">` inside Markdown. There's no build step and no bundler.
- The pinned `@duckdb/duckdb-wasm` version and `EXT_VERSION` are an **ABI-matched pair** that must track
  duckdb-miint's `duckdb/` submodule; the comment above `EXT_VERSION` records the current pair. When
  upstream bumps DuckDB, bump both together and confirm the matching build exists under
  `ftp.microbio.me/pub/miint/tagged/<version>/wasm_eh/`.
- miint is published only for `wasm_eh` and is unsigned (hence `allowUnsignedExtensions`).
- Deliberate, do not "simplify" away: no `castBigIntToDouble` (keeps integers above 2^53 exact);
  results are read column-wise up to `MAX_ROWS` instead of `table.toArray()`; after each statement,
  new `miint_warnings()` rows are shown under it. miint reports skipped work (e.g. an ENA run that
  failed to download) as a warning, the statement still succeeds, and stderr is invisible in a browser.

### Deployment
`.github/workflows/deploy.yml` installs `requirements.txt`, syncs, runs `mkdocs build --strict`, and
deploys to GitHub Pages on push to `main`, nightly (09:17 UTC), `workflow_dispatch`, and
`repository_dispatch: docs-updated`. **Pushing to `main` publishes the live site.**

`requirements.txt` pins Material and pymdown-extensions. Material 9.x requires `mkdocs<2`; the
MkDocs 2.0 banner it prints during builds is informational, not an error.

## Verification

- `mkdocs build --strict` is the gate the deploy workflow enforces for content, nav, and config changes.
- `make test` builds the site, then runs the playground's browser tests (`tests/playground/`: Node's
  built-in runner plus puppeteer-core driving headless Chrome). It needs Node 22.12+ and Chrome;
  set `CHROME_PATH` to use another binary and `SITE_DIR` to test another build.
  `.github/workflows/playground-tests.yml` runs them on playground-related changes. It is
  deliberately not a deploy gate.
- The tests drive the page as a user does, never by reaching into its code. Write the failing test
  first for any playground behavior change, and check that it fails against the old page. Use
  `/__slow/<name>.csv` (in `harness.mjs`) for a statement whose duration must not depend on CPU speed.
- They need the network (jsDelivr, ftp.microbio.me, ENA's Portal API). The warnings tests are
  explicitly skipped, with the reason, when ENA's Portal API is unreachable. That skip is legitimate;
  never make an unreachable dependency pass silently.
- Not yet covered: history, continuation prompts, clear, BIGINT exactness, the `MAX_ROWS` cap.
  Verify those by hand if you touch them.

## Rules

These rules apply to every task in this project unless explicitly overridden.

### Rule 1 — Think Before Coding
Bias: caution over speed on non-trivial work.
State assumptions explicitly. Ask rather than guess.
Push back when a simpler approach exists. Stop when confused.

### Rule 2 — Simplicity First
Minimum code that solves the problem. Nothing speculative.
No abstractions for single-use code.

### Rule 3 — Surgical Changes
Touch only what you must. Don't improve adjacent code.
Match existing style. Don't refactor what isn't broken.

### Rule 4 — Goal-Driven Execution
Define success criteria. Loop until verified.

### Rule 5 — Surface conflicts, don't average them
If two patterns contradict, pick one (more recent / more tested).
Explain why. Flag the other for cleanup.

### Rule 6 — Read before you write
Before adding code, read exports, immediate callers, shared utilities.
If unsure why existing code is structured a certain way, ask.

### Rule 7 — Tests verify intent, not just behavior
Tests must encode WHY behavior matters, not just WHAT it does.
A test that can't fail when business logic changes is wrong.

### Rule 8 — Checkpoint after every significant step
Summarize what was done, what's verified, what's left.
Don't continue from a state you can't describe back.

### Rule 9 — Match the codebase's conventions, even if you disagree
Conformance > taste inside the codebase.
If you think a convention is harmful, surface it. Don't fork silently.

### Rule 10 — Fail loud
"Completed" is wrong if anything was skipped silently.
Don't silently skip tests or checks you caused to be skipped (commented out, xfail'd, missed).
Default to surfacing uncertainty, not hiding it.
